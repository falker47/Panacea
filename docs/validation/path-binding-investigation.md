# Path-binding investigation

Read-only pre-patch investigation, 2026-10-12. Product code and tests were not edited, and no tests, native write probes, maintenance commands or GUI were run. This is a strategy report, not a verification result. Line references describe the source inspected before the parent patch.

## Facts and source-to-sink path

- `modules/cleanup.py:42-69` opens the leaf with OPEN_REPARSE_POINT, denies sharing write/delete, then performs one reparse-attribute check. `_guard_path` (`:75-85`) holds ancestors but discards their handles from its public result. `_walk_directory` (`:161-188`) subsequently uses pathname-based `scandir` and `lstat`. `_delete_file` (`:150-159`) sets disposition on the opened file handle, whose actual normalized path is never checked.
- The controller reports a native fixture failure for `tests/test_cleanup.py::test_alternate_reparse_access_masks_never_escape_live_guard[256]`. Its implementation (`:220-236`) tries FILE_WRITE_ATTRIBUTES (0x100) against a held guard and performs no deletion. This directly contradicts the guard's claim to prevent all in-place reparse conversion. I did not rerun it.
- Approval is lexical: `_approved_temp`, `_local_root`, `_browser_paths`, and `_delete_folder_contents` derive narrowly allowed Temp/cache paths (`modules/cleanup.py:98-148, :227-240`). A redirected ancestor can therefore make an approved string open an unapproved object.
- The shared sibling is Turbo: `_storage_directory` (`modules/performance.py:107-129`) creates missing directories by path; `_load_state` (`:78-103`) checks by path then reopens with `read_text`; `_save_state` (`:134-149`) creates/writes a NamedTemporaryFile and finally deletes by path; `_replace_snapshot` (`:151-181`) reopens its source and performs a native handle rename. A fix confined to cleanup traversal or the final rename leaves these sibling operations dependent on the broken guard assumption.

## Narrow complete strategy and limits

1. Make a shared opened-object validator the enforcement boundary. Bind every opened ancestor, directory and file to its immutable expected approved path before yielding the handle, reading/counting it, or issuing disposition. Query `GetFinalPathNameByHandleW` with FILE_NAME_NORMALIZED and VOLUME_NAME_DOS; reject errors, truncation, unexpected namespace and mismatches. Microsoft documents that normalized final paths resolve symbolic-link targets and that the returned DOS path uses the extended prefix. Do not use FILE_NAME_OPENED. [API documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew).
2. Do not derive the expected path by resolving the candidate after a potential ancestor retarget. That would authorize the attacker's destination. Start from the approved lexical path, reject unsupported aliases or explicitly establish a trusted canonical representation, and extend it by each validated entry name. Existing UNC/device-root refusal stays intact. Short names, SUBST drives, trailing-dot/space spellings and extended prefixes require explicit handling or fail-closed rejection; stripping arbitrary prefixes or `realpath`-normalizing both sides is unsafe.
3. If path equality uses `normcase`, reject case-sensitive directory namespaces at every ancestor and traversal level; otherwise distinct case-only siblings may collapse into the same comparison. Keep checks live around path-based enumeration, including Firefox `listdir`, and before advancing to children. Windows supports per-directory case sensitivity, so it cannot be assumed absent. [Microsoft case-sensitivity documentation](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity). An unsupported query must not silently mean case-insensitive. README promises Windows 10/11; verify behavior on supported Windows 10 builds.
4. Rechecking held guards before/after `scandir` improves rejection but is not an atomic traversal boundary. An attacker may briefly retarget and restore. Every selected child still needs final opened-object binding; preview/counting and deletion must use the validated handle's metadata, with one-link and regular-file checks preserved. Handle-based enumeration or relative opens would provide a stronger traversal boundary if strict exclusion of even outside-name enumeration is required.
5. Turbo must read the snapshot through its validated open handle and retain the original 16 KiB limit, JSON validation, fail-closed error behavior and durable-save-before-settings-mutation ordering. A path `lstat` followed by `read_text` retains a check/use gap even with improved ancestor checks.
6. Own one temporary-file handle through creation, validation, payload write, flush, native rename and failure disposal. Do not close/reopen it for the rename or call pathname `exists`/`unlink` in `finally`; a replacement entry must never become cleanup's target. Exclusive creation must not overwrite a collision. Source handle identity must remain continuous, and cleanup after an exception must dispose only that owned temporary object.
7. Distinguish validating an existing object before mutation from validating a new object after creation. Path-based `mkdir` and NamedTemporaryFile creation can already create an outside entry before final-path validation. To claim no outside write at all, bind creation to the retained approved parent directory object (handle-relative native creation) or prove an equivalent atomic constraint. Guard checks around path-based creation alone do not establish that property. If instead the accepted invariant permits creating and disposing an owned empty temporary file before validation, document that narrower guarantee explicitly; it does not justify writing snapshot payload before validation.
8. Preserve the existing native same-parent rename: a simple filename plus null RootDirectory keeps the source in its existing parent directory, and replacement remains atomic. Validate the source before rename, use only a simple destination component, and avoid reopening the destination by absolute path. Microsoft explicitly documents this rename form. [FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information). A successful rename must transfer ownership so failure cleanup cannot delete the committed snapshot.

## Necessary regression evidence

- Keep the access-mask fixture as evidence of OS capability; the corrected safety assertion should require rejection before outside enumeration/counting/disposition, rather than claim every FILE_WRITE_ATTRIBUTES conversion is blocked. Cover 0x100 in addition to GENERIC_WRITE and a legitimate conversion control.
- Retarget while an ancestor/root guard is alive and before opening the approved leaf; exercise nested-directory preview, real cleanup of fixture-only ordinary entries, and Firefox profile discovery. Add a retarget just after an initial guard check so safety is not explained only by a precheck. Preserve an outside sentinel and exact inside totals.
- Cover normalized-path mismatch, query failure/truncation, alias spelling, mixed-case ordinary names, and case-sensitive ancestor/child rejection. If aliases are intentionally unsupported, assert a clear refusal rather than accidental success.
- For Turbo, attempt retarget before missing-directory creation, temporary creation, snapshot read, source rename and failure cleanup. A failed save must leave all mocked settings untouched and preserve the prior snapshot; a colliding/replaced temporary entry must remain untouched. No outside snapshot payload may be written.
- Preserve existing legitimate controls: nested two-file cleanup `(2, 8)`, preview `(1, 3)` without mutation, locked-file skips, hardlink refusal, browser Bookmarks preservation (`tests/test_cleanup.py`); custom power/service/visual restoration after restart, failed-save mutation refusal, master Turbo restore and cross-process mutex/reload/abandonment (`tests/test_performance.py`). Add a direct native atomic snapshot replacement under the live guards, including an existing destination, and ensure no owned temporary remains after normal success/failure.
- Suggested parent validation: focused cleanup/performance pytest cases first, then `python -m pytest tests/test_cleanup.py tests/test_performance.py -q` with an approved disposable fixture base; relevant Ruff and compile checks afterward. These commands were not run by this investigator.
